# 問題読み込み・問読み・CPU早押しの設計（案）

実装前の設計メモです。2つのシステムに分けます。

```
┌──────────────────────────┐   問題集.json   ┌─────────────────────────┐
│ ① 問題情報生成システム     │ ─────────────▶ │ ② クイズアプリ（QUIZ KNIGHTS）│
│ （このPC。アプリの外）     │                 │  取り込み・表示・早押し・CPU │
└──────────────────────────┘                 └─────────────────────────┘
```

- ①は、問題集（CSV・テキストなど）から、②が読む JSON を作ります。AI（ローカルLLM、または Claude）を使えます。
- ②は、JSON を受け取って使うだけです。AI の種類を変えても、②は変えません。
- 受け渡しは**ファイル（JSON）だけ**です。サーバーも鍵も要りません。

## 1. 問題集 JSON の形式

```json
{
  "version": 1,
  "title": "サンプル問題集",
  "questions": [
    {
      "no": 1,
      "q": "日本で一番高い山は何でしょう？",
      "a": "富士山",
      "alt": ["ふじさん", "富士"],
      "wrong": ["北岳", "穂高岳", "立山"],
      "cuts": [4, 8, 12],
      "sure": 8,
      "reading": null
    }
  ]
}
```

| 項目 | 必須 | 意味 |
|---|---|---|
| `no` | ○ | 問題番号（出題順の目安。重複不可） |
| `q` | ○ | 問題文 |
| `a` | ○ | 正解 |
| `alt` | | 正解として認める別表記 |
| `wrong` | | 誤答の候補（CPU が誤答するときに、それらしい答えを出す） |
| `cuts` | ○ | スラッシュの位置。`q` の先頭からの文字数（昇順、1〜`q`の長さ−1） |
| `sure` | | 確定ポイント。そこまで読めば答えが一意に絞れる位置（文字数）。省略時は CPU が使えない |
| `reading` | | 読み上げ用の読み仮名（将来の読み上げ用。今は未使用） |

取り込み時のチェック: 空の `q`/`a`、範囲外の `cuts`、重複した `no`、`sure` が範囲外、は警告して弾く。

## 2. クイズアプリ（②）

### 2-1. 取り込みと保存
- 進行役が、部屋の準備画面で JSON を選ぶ（ファイル選択・貼り付け）。
- 保存先は端末内（localStorage、量が多ければ IndexedDB）。**問題文はサーバーに送らない**。参加者に漏れず、サーバーの保存量も増えない。
- 一覧と、1問ごとの編集（スラッシュ・確定ポイントの移動、誤答候補の編集）ができる。

### 2-2. 管理者の画面に問題文を表示（カラオケ表示）
1. 受付が始まると、問題文が出る。**進行役が、キーやボタンで1塊ずつ送る（手動送りが既定）**と、塊ごとに色が進む。読むペースは進行役が決める。自動送り（速さは文字/秒）は、将来のオプション。
2. 誰かが押したら進行が止まり、そこまでを「ここまで読んだ」と強調する。
3. 回答中は止まったまま。誤答で受付が再開したら、続きから進める（または次の塊から）。
4. 参加者の画面には**出さない**（決定）。文字で読めてしまい、早押しの条件が変わるため。

### 2-3. 問読み
- 読むのは進行役（人間）。画面の進行は、読むペースの目安（ペースメーカー）。
- 進行は**手動送りが既定**（決定）。読むスピードに合わせるのは進行役の操作。
- 将来、読み上げ（Web Speech、VOICEVOX）を足せる。塊ごとに1つずつ話させ、塊の切れ目で止める。

### 2-4. 押した位置の判定
- 手動送りなので、位置は、**進行役が塊を送った時刻の記録**と、サーバーが補正した押下時刻から決める（押した時点で表示されていた塊まで、を読んだ位置とする）。送った時刻は進行役の端末が持ち、サーバー時刻に換算する。
- 既存の早押し判定（`server/buzz.js`）はそのまま使う。

### 2-5. CPU の早押し
- CPU ごとに「反応の速さ」「ばらつき」「誤答しやすさ」を持つ。
- 押す位置は、`sure`（確定ポイント）を基準に決める。強い CPU は直前、弱い CPU は過ぎてから。確定前に押して誤答するパターンも確率で混ぜる。
- 正誤は「押した位置が `sure` 以降か」で決める。誤答は `wrong` から選ぶ。
- CPU の押下は、進行役の端末から、参加者の押下と同じ形式でサーバーに入れる。判定は共通。
- 割り切り: CPU は知識で答えているのではなく、位置で正誤を決めている。

## 3. 問題情報生成システム（①）

### 入力
- CSV（問題文,答え）、テキスト（1行1問）、スラッシュ入りテキスト（`日本で/一番高い/山は…`）など。

### 処理（段階的に）
1. **区切り**: BudouX（OSS、日本語の文節分割）で機械的に下書きを作る。AI に直させてもよい。
2. **AI による付与**: 問題文と正解を LLM に渡し、確定ポイント・別表記・誤答候補・読み仮名を JSON で出させる。
3. **検査**: 範囲外・重複などを検査し、問題のある行を一覧にする。
4. **出力**: 問題集 JSON を書き出す。

### 実行場所
- このPCのローカルLLM（Ollama など）、または Claude（Claude Code に頼む）。
- ①は、②の画面からは呼ばない。ファイルを介して使う。

### 確認の手順
- AI の出力は下書き扱い。②の編集画面で確認・修正してから使う。
- 確定ポイントは、答えが複数あり得る問題で判断が割れる。人が確認する前提にする。

## 4. 進め方（段階）

| 段階 | 内容 | 確認すること |
|---|---|---|
| 1 | JSON の取り込み、一覧、編集画面 | 形式の検査が十分か |
| 2 | 管理者画面のカラオケ表示、押下位置の計算 | 進行の速さと止まり方の感触 |
| 3 | CPU の早押し（`sure` 基準） | 強さの調整、体感の自然さ |
| 4 | ①の作成（BudouX → AI 付与 → 検査） | AI の精度、手直しの量 |
| 5 | 読み上げ（Web Speech → 必要なら VOICEVOX） | 声の自然さ、読み間違い |

段階1〜3は、手書きの JSON で動く。①は後から差し込める。

## 5. 決めること

- 問題の保存先（localStorage か IndexedDB か）。問題集の大きさの目安。
- 出題順（番号順、ランダム、1問ごとの選択）。ジャンル選択（既存の怪盗の能力）との関係。
- 誤答候補を CPU 以外に使うか（例: 四択モード）。

## 6. 決定済み

- 進行は**手動送り**（自動送りは将来のオプション）。
- 参加者の画面には**問題文を出さない**。
- 確定ポイント `sure` は**文字数**で持つ。スラッシュを直しても、確定ポイントの位置は変わらない。ただし、押した位置は塊の切れ目で扱うので、CPU の判定は「押した時点の読み済み文字数 ≥ `sure`」で比べる。
